Módulo 1 • Setup Supabase

Tarefa de referência

Entrega que você precisa saber defender

Criou a base de conexão exclusiva da v2, separando desenvolvimento local e cloud e impedindo que uma chave administrativa entrasse no navegador.

Entenda as três peças da infraestrutura

Supabase reúne serviços, mas cada peça tem uma função. PostgreSQL armazena dados e executa constraints, políticas e funções. Auth verifica credenciais e mantém sessões. A Data API transforma chamadas HTTP do SDK em operações de banco. Next.js executa a aplicação, tanto no navegador quanto no servidor. Uma conexão bem-sucedida não prova que todas essas peças estão integradas corretamente.

Ambientes e migrations

Local e cloud são bancos distintos. A migration é um arquivo SQL versionado que descreve uma evolução do banco. Aplicar a mesma sequência de migrations ajuda a reproduzir a estrutura; não copia automaticamente os dados de um ambiente para outro. No FixIt v2 foi criado projeto próprio, sem importar credenciais ou funcionalidades da versão antiga. Os arquivos ignorados de ambiente escolhem URL e chave. Uma URL correta com uma chave de outro projeto ainda pode falhar: validar formato não valida a combinação no serviço.

Chave publicável não é a senha de um usuário

A chave publicável permite que um cliente alcance o projeto dentro das permissões públicas. O token de uma sessão identifica uma pessoa autenticada. RLS e RPCs decidem o que essa pessoa pode fazer. A chave administrativa tem poderes diferentes e não pode entrar no bundle público. Prefixo NEXT_PUBLIC indica valor que pode chegar ao navegador; por isso a configuração faz uma validação antes da compilação.

Leia a configuração com intenção

Em src/lib/supabase/config.ts, siga environment → URL → chave → retorno. Local exige loopback; cloud exige HTTPS fora de loopback. URL com credenciais, caminho ou parâmetros é recusada. A validação aceita sb_publishable_ e, somente local, anon legado. Reconhecer o formato não é verificar criptograficamente a chave; a conexão real confirma se ela funciona.

Como raciocinar sobre o healthcheck

setup_healthcheck é uma RPC pública intencional que devolve um marcador. Não lê tabelas de negócio. Se ela funciona e uma solicitação não aparece, investigue sessão, ambiente e autorização em vez de concluir que o banco caiu. Se ela falha, separe URL, rede, chave, disponibilidade e migration ausente antes de alterar políticas.

Módulo 2 • Tabelas principais

Tarefa de referência

Entrega que você precisa saber defender

Modelou a identidade, a solicitação e seu histórico com integridade no PostgreSQL.

Modelo de dados como contrato

Uma tabela não é só um conjunto de campos. Ela define o que pode existir. profiles representa a pessoa no produto e referencia a conta de Auth. solicitacoes representa o pedido. historico representa acontecimentos imutáveis desse pedido. E-mail e senha ficam em Auth; perfil contém nome, papel, atividade e data. Essa separação evita misturar credencial com regra de negócio.

Por que validar no banco

TypeScript ajuda durante desenvolvimento, mas desaparece como barreira para quem faz uma requisição direta. A validação do formulário melhora a experiência; o banco protege dados de qualquer cliente. NOT NULL impede ausência; CHECK valida condições da linha; enum limita valores; FK exige que referências existam. Triggers acrescentam regras que precisam comparar outras linhas ou impedir mutações específicas.

Identidade e referências

A PK identifica uma linha. Uma FK liga linhas sem copiar toda a entidade. solicitante_id e responsavel_id apontam para profiles; historico aponta para solicitação e autor. O UUID é identidade interna, enquanto numero oferece referência humana. Uma sequência pode avançar em uma transação que depois falha; uma lacuna não prova perda de solicitação.

Estado válido não é transição autorizada

A restrição que exige prioridade e responsável em Em atendimento/Concluída verifica uma combinação armazenada. Ela não decide, sozinha, se um Cliente pode concluir uma solicitação. Essa segunda pergunta depende do ator, do estado anterior e da operação: pertence às RPCs. Conseguir separar integridade de autorização é essencial para explicar o desenho.

Imutabilidade e preservação

Papel é fixo no MVP. Histórico é somente acréscimo: corrigir observação significa adicionar outra. Desativação mantém autoria e atribuições anteriores, mas impede acesso e novas atribuições ao inativo. FKs restritivas bloqueiam exclusões que destruiriam o contexto. Um administrador ainda pode realizar manutenção explícita com poderes especiais; a aplicação não oferece esse caminho.

Índices e limites

Índice acelera buscas por chaves usadas nas consultas, com custo de armazenamento e escrita. Não substitui autorização nem validação. A migration indexa vínculos relevantes e ordenação do histórico. Limites acordados: nome 120, título 150, local 200, descrição e observação 5000. Categoria, anexos e setor não devem ser inventados a partir de documentos da versão antiga.

Módulo 3 • Autenticação

Tarefa de referência

Entrega que você precisa saber defender

Entregou cadastro, login, contexto autenticado, logout e provisão técnica da equipe.

Autenticar e autorizar são perguntas diferentes

Autenticar responde quem é a pessoa. Autorizar responde se essa pessoa pode acessar o produto, determinada linha e determinada ação agora. Um JWT válido não transforma um perfil inativo em operador autorizado. createAuth.context primeiro usa getUser para obter identidade validada e depois consulta profiles. O papel vem do banco.

Cadastro atômico

O wrapper aceita nome, e-mail e senha, rejeita propriedades extras e envia nome em options.data. O banco define o papel de Cliente e cria o perfil por trigger na inserção da conta Auth. Se o perfil falha dentro dessa transação, a conta não deve permanecer órfã. Duas chamadas independentes na aplicação — criar conta e depois criar perfil — teriam uma janela de inconsistência.

Metadados são entrada, não autoridade

Um cliente pode tentar chamar Auth diretamente e forjar metadados. Rejeitar papel no wrapper é útil, mas a proteção real precisa sobreviver a esse desvio. user_metadata é editável pelo usuário; o desenho não o usa para conceder privilégio. Gestor e Manutentor são provisionados pelo procedimento técnico, não por um seletor público.

Cookies e renderização no servidor

O navegador mantém cookies de sessão. O cliente browser conhece a sessão; o cliente server lê cookies da requisição. Cookies renovados precisam chegar ao processamento atual e à resposta para o navegador. O proxy faz essa ponte. Em Server Components a gravação pode não ser permitida; mutações de Auth devem ocorrer em contexto que possa escrever cookies, como Route Handler ou Server Action.

Renovação e logout

Access token tem duração limitada. Refresh token permite obter nova sessão e pode sofrer rotação. Logout com scope local encerra a sessão atual e sua renovação; não promete apagar instantaneamente a validade criptográfica de todo JWT já emitido nem sair de todos os dispositivos. A autorização por perfil atual no banco continua importante.

Erros que a tela precisa distinguir

invalid_input indica entrada recusada; invalid_credentials indica credenciais inválidas; not_authenticated indica ausência de sessão válida; unavailable agrupa indisponibilidade. profile_missing pode significar que RLS ocultou um perfil inativo. Não prometa que todo inativo retorna profile_inactive. O consumidor verifica ok antes de acessar user/profile.

Por que private, no-store

Resposta que depende da identidade não deve ser reaproveitada como conteúdo público compartilhado. O proxy define Cache-Control para impedir armazenamento desse conteúdo. Essa medida complementa a autorização e não cria autorização por si só. Testar dois contextos de navegador verifica se o contexto anônimo permanece separado do autenticado.

Módulo 4 • RLS e operações autorizadas

Tarefa de referência

Entrega que você precisa saber defender

Implementou isolamento de dados por pessoa e papel e operações estreitas de escrita.

RLS é um filtro do banco

Row Level Security aplica políticas às linhas acessíveis. O filtro da tela serve para navegação; RLS limita o universo que a consulta pode enxergar. Assim, count, filtros e paginação devem operar sobre linhas visíveis. Saber o UUID de uma solicitação alheia não concede acesso.

Matriz de leitura do FixIt

Cliente vê solicitações próprias. Gestor vê todas. Manutentor vê as atualmente atribuídas. Histórico herda a visibilidade da solicitação, inclusive eventos anteriores à atribuição atual. Perfis são visíveis quando necessários para identificar pessoas relacionadas; Gestor também consulta Manutentores ativos para atribuir. Isso não abre um diretório geral de pessoas.

Privilégio de tabela e política são camadas

GRANT SELECT permite tentar ler a tabela; a política define quais linhas passam. As tabelas não permitem INSERT/UPDATE/DELETE direto à aplicação. Não se resolve um erro de gravação liberando DML geral: o contrato exige RPCs. Visitante não tem SELECT de negócio; sessão sem perfil ativo não obtém linhas.

Por que existem duas camadas de função

A RPC pública é security invoker. Ela encaminha uma operação delimitada à implementação privada security definer, que executa com os privilégios do dono da função. Essa capacidade é sensível: a função precisa revalidar auth.uid, papel, atividade, alvo e estado. Schema privado, nomes qualificados, search_path vazio e permissões explícitas reduzem a superfície disponível. Só estar em private não basta se houver privilégios indevidos.

Autorização acompanha o estado atual

Depois de reatribuir, o responsável anterior perde acesso nas próximas operações; dados que já foram entregues ao navegador não podem ser magicamente recolhidos. A RPC trava a solicitação e avalia o responsável atual. Isso impede decidir com uma responsabilidade que ficou desatualizada durante uma operação concorrente.

Leitura negada e escrita negada têm formas diferentes

Uma consulta autorizada sem linha visível pode retornar lista vazia. Uma RPC pode retornar 42501 para ação não autorizada. Não conclua que um ID não existe só porque veio vazio: também pode estar fora do acesso. Não revele detalhes adicionais para tentar distinguir essas situações na interface.

Módulo 5 • Persistência e histórico

Tarefa de referência

Entrega que você precisa saber defender

Validou o fluxo transacional de solicitações e a rastreabilidade de cada alteração.

Uma RPC é uma operação de negócio

Em vez de o navegador montar várias gravações, ele pede uma operação: abrir, transicionar, organizar ou observar. O servidor escolhe autoria, datas e efeitos. Uma chamada ao PostgreSQL executa no contexto transacional: se uma exceção interrompe a operação, suas alterações não devem ficar parcialmente persistidas.

Siga uma abertura

O Cliente envia título, descrição e local. O banco obtém o operador ativo a partir de auth.uid, confirma papel Cliente, insere solicitação para o próprio operador e grava abertura. O cliente não informa solicitante, autor ou data. Isso evita fabricar solicitações em nome de outra pessoa por parâmetros extras.

Siga a triagem e o atendimento

Gestor transforma Pendente em Aprovada ou Descartada. Em Aprovada, Gestor pode organizar prioridade e responsável. O responsável atual inicia atendimento e depois conclui; prioridade e responsável são obrigatórios nesses estados. Gestor não recebe automaticamente todas as ações do Manutentor. Terminal não reabre e não aceita nova observação.

Par completo e comparação com null

organizar_solicitacao recebe prioridade e responsável desejados, inclusive quando null. null remove o campo, respeitadas as restrições. IS DISTINCT FROM compara valores tratando null de forma definida: null e null não diferem, null e valor diferem. Só campos alterados geram eventos. Trocar os dois gera dois eventos na mesma transação.

Atomicidade com um exemplo de falha

Suponha que prioridade mude de baixa para alta e responsável de M1 para M2. O banco atualiza a solicitação, insere o evento de prioridade e falha ao inserir o evento de responsável. O correto é desfazer atualização e primeiro evento. O teste induz uma falha controlada no segundo evento e consulta o estado persistido depois; contar apenas um erro na resposta não provaria rollback.

Locks e concorrência

FOR UPDATE trava a linha da solicitação para que operações concorrentes esperem e decidam sobre o estado vigente. FOR SHARE no perfil coordena a operação com sua inativação. Não significa que o banco inteiro fica parado. Locks têm escopo e duração transacional. O cálculo de data também precisa estar dentro da mesma seção protegida para não usar um último evento obsoleto.

Repetição depois de falha de rede

O banco pode concluir e a resposta se perder. Repetir uma observação cria outro registro, pois não há chave de idempotência. Uma transição repetida pode ser recusada porque o estado já mudou. O consumidor deve reconsultar e decidir como informar a pessoa, separando falha de transporte de recusa de negócio.

O que este cartão acrescentou de fato

As operações principais já estavam implementadas na entrega de RLS. O cartão de persistência aprofundou sua validação e não precisou criar nova migration naquele momento. Ao relatar trabalho, diga o que foi implementado antes, o que foi validado aqui e qual correção veio depois. Não invente código novo para cada cartão.

Módulo 6 • Revisão de integração e segurança

Tarefa de referência

Entrega que você precisa saber defender

Conferiu o backend completo que as duas frentes visuais consumirão e corrigiu falhas encontradas.

Teste por camada

Teste unitário isola um comportamento pequeno. Teste de integração usa serviços reais e confere combinações. O runner RLS autentica pessoas reais e chama API/RPC; SQL privilegiado prepara e limpa fixtures, não faz a operação no lugar do usuário. O runner Next usa app temporário com os módulos reais, build de produção e Chromium. Cada camada responde a perguntas diferentes.

O defeito de relógio

A revisão observou evento posterior com horário anterior: recuo de 132,416 ms. O executor avançava em tempo monotônico e os dados batiam com as operações. Um probe reproduziu a falha. Ordenar por created_at e id não conserta um horário que voltou: o segundo critério só resolve empate, não uma inversão de data.

Correção e seu limite

proxima_data_historico calcula greatest(clock_timestamp(), criação da solicitação, último evento +1 microssegundo). O lock por solicitação serializa a leitura do último evento e a gravação seguinte. A ordem é estritamente crescente por solicitação nas RPCs. Datas podem ficar à frente do relógio físico após um recuo. Não há promessa de ordem global entre solicitações nem correção retroativa de dados antigos.

Regressão determinística

A preparação privilegiada posiciona apenas o evento inicial de uma fixture uma hora no futuro. As próximas operações continuam passando pelas RPCs públicas. Antes da correção o teste falha; depois passa. Isso reproduz o risco sem mudar relógio do sistema. Também foram registradas 100 sequências completas de nove eventos após a correção.

Limpeza é parte da confiabilidade do teste

Um runner pode falhar ao fechar navegador, servidor ou diretório temporário. Se isso impedir a limpeza SQL, deixa dados e sessões de teste. A correção isola falhas e sempre tenta a limpeza SQL, sinalizando saída não zero se algo falhar. Fixtures são dados controlados e identificáveis criados só para o teste; limpar significa conferir sua ausência, não presumir que um finally resolveu tudo.

Evidência tem data e alcance

Na revisão final constam 295 verificações RLS, 25 Next e 32 Auth por ambiente. Verify tinha 14 testes, lint, tipos e build. São resultados históricos de 10–14/11; não descrevem uma execução feita ao abrir este guia. Quantidade não prova cobertura completa. Fingerprints iguais comparam os objetos selecionados; advisors sem achados e audit sem vulnerabilidades conhecidas não são prova formal de ausência de risco.

Explique o teste de renovação com precisão

O runner antecipou o vencimento guardado no cookie mantendo token assinado e refresh real, observando rotação. Isso não é esperar uma hora de expiração natural. Novo contexto de navegador com cookies persistidos prova persistência além da instância em memória. Revogação e isolamento foram cenários separados.

export function getSupabaseConfig(env: Environment) {
  const environment = env.NEXT_PUBLIC_SUPABASE_ENV;
  if (environment !== "local" && environment !== "cloud") {
    throw new Error("NEXT_PUBLIC_SUPABASE_ENV deve ser local ou cloud.");
  }
  const url = env.NEXT_PUBLIC_SUPABASE_URL;
  if (!url) throw new Error("Configure NEXT_PUBLIC_SUPABASE_URL.");
  let parsed: URL;
  try {
    parsed = new URL(url);
  } catch {
    throw new Error("NEXT_PUBLIC_SUPABASE_URL deve ser uma URL válida.");
  }
  const loopback = ["localhost", "127.0.0.1", "[::1]"].includes(parsed.hostname);
  if (environment === "local" ? !loopback || !["http:", "https:"].includes(parsed.protocol) : loopback || parsed.protocol !== "https:") {
    throw new Error("URL incompatível com o ambiente: local exige loopback; cloud exige HTTPS fora de loopback.");
  }
  if (parsed.username || parsed.password || parsed.pathname !== "/" || parsed.search || parsed.hash) {
    throw new Error("NEXT_PUBLIC_SUPABASE_URL deve conter apenas a origem, sem credenciais, caminho ou parâmetros.");
  }
  const publishableKey = env.NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY;
  if (!publishableKey) throw new Error("Configure NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY.");
  validateSupabasePublishableKey(publishableKey, environment);
  return { environment, url, publishableKey };
}

export function validateSupabasePublishableKey(publishableKey: string, environment: string | undefined) {
  let legacyAnon = false;
  if (publishableKey.startsWith("eyJ")) {
    try {
      legacyAnon = JSON.parse(atob(publishableKey.split(".")[1].replace(/-/g, "+").replace(/_/g, "/"))).role === "anon";
    } catch {
      // Chaves malformadas são recusadas abaixo sem imprimir seu conteúdo.
    }
  }
  if (!publishableKey.startsWith("sb_publishable_") && !(environment === "local" && legacyAnon)) {
    throw new Error("Use uma chave publicável sb_publishable_; apenas local aceita a chave anon legada. Chaves privilegiadas são proibidas.");
  }
}

import type { SupabaseClient } from "@supabase/supabase-js";

export type AuthError = "invalid_input" | "invalid_credentials" | "not_authenticated" | "profile_missing" | "profile_inactive" | "profile_creation_failed" | "signup_failed" | "unavailable";
export type Profile = { id: string; nome: string; papel: "cliente" | "gestor" | "manutentor"; ativo: boolean; created_at: string };
export type AuthResult = { ok: true; user: { id: string; email: string | undefined }; profile: Profile } | { ok: false; error: AuthError };
const failure = (error: AuthError): AuthResult => ({ ok: false, error });

function credentials(input: unknown, signup: boolean): input is { nome: string; email: string; password: string } {
  if (!input || typeof input !== "object") return false;
  const value = input as Record<string, unknown>;
  const keys = signup ? ["nome", "email", "password"] : ["email", "password"];
  if (Object.keys(value).some(key => !keys.includes(key))) return false;
  return typeof value.email === "string" && /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(value.email.trim())
    && typeof value.password === "string" && value.password.length > 0
    && (!signup || (typeof value.nome === "string" && value.nome.trim().length > 0 && [...value.nome].length <= 120));
}

function providerError(error: { code?: string; status?: number }, signup = false): AuthResult {
  if (error.code === "invalid_credentials") return failure("invalid_credentials");
  if (signup && error.code === "unexpected_failure") return failure("profile_creation_failed");
  if (error.code === "user_already_exists") return failure("signup_failed");
  if (error.code === "weak_password" || error.code === "email_address_invalid" || error.code === "validation_failed") return failure("invalid_input");
  if (error.status === 429) return failure("unavailable");
  if (error.status && error.status < 500) return failure(signup ? "signup_failed" : "invalid_credentials");
  return failure("unavailable");
}

export function createAuth(client: SupabaseClient) {
  async function context(): Promise<AuthResult> {
    try {
      const { data, error } = await client.auth.getUser();
      if (error) {
        if (["session_not_found", "refresh_token_not_found", "refresh_token_already_used", "bad_jwt"].includes(error.code ?? "") || error.name === "AuthSessionMissingError" || error.status === 401 || error.status === 403) return failure("not_authenticated");
        return failure("unavailable");
      }
      if (!data.user) return failure("not_authenticated");
      const profile = await client.from("profiles").select("id,nome,papel,ativo,created_at").eq("id", data.user.id).maybeSingle();
      if (profile.error) return failure("unavailable");
      if (!profile.data) return failure("profile_missing");
      if (!profile.data.ativo) return failure("profile_inactive");
      return { ok: true, user: { id: data.user.id, email: data.user.email }, profile: profile.data as Profile };
    } catch {
      return failure("unavailable");
    }
  }
  return {
    context,
    async signUp(input: unknown): Promise<AuthResult> {
      if (!credentials(input, true)) return failure("invalid_input");
      try {
        const { data, error } = await client.auth.signUp({ email: input.email.trim(), password: input.password, options: { data: { nome: input.nome.trim() } } });
        if (error) return providerError(error, true);
        if (!data.session) return failure("signup_failed");
        return await context();
      } catch {
        return failure("unavailable");
      }
    },
    async signIn(input: unknown): Promise<AuthResult> {
      if (!credentials(input, false)) return failure("invalid_input");
      try {
        const { error } = await client.auth.signInWithPassword({ email: input.email.trim(), password: input.password });
        if (error) return providerError(error);
        return await context();
      } catch {
        return failure("unavailable");
      }
    },
    async signOut(): Promise<{ ok: true } | { ok: false; error: AuthError }> {
      try {
        const { error } = await client.auth.signOut({ scope: "local" });
        return error ? { ok: false, error: "unavailable" } : { ok: true };
      } catch {
        return { ok: false, error: "unavailable" };
      }
    },
  };
}

export async function proxy(request: NextRequest) {
  const { url, publishableKey } = getPublicSupabaseConfig();
  let response = NextResponse.next({ request });
  const client = createServerClient(url, publishableKey, {
    cookies: {
      getAll: () => request.cookies.getAll(),
      setAll(values, headers) {
        values.forEach(({ name, value }) => request.cookies.set(name, value));
        response = NextResponse.next({ request });
        values.forEach(({ name, value, options }) => response.cookies.set(name, value, options));
        Object.entries(headers).forEach(([key, value]) => response.headers.set(key, value));
      },
    },
  });
  await client.auth.getUser();
  response.headers.set("Cache-Control", "private, no-store");
  return response;
}

Como reproduzir uma evidência sem confundir ambientes

Primeiro leia README e o relatório da tarefa. Confira Node/npm fixados, dependências instaladas e o ambiente escolhido. Nunca copie credenciais para o material. Não execute runners cloud sem entender o procedimento de fixtures, o helper SQL e a limpeza. Uma execução parcial sem limpeza confirmada não equivale a aprovação.

npm run verify
npm run supabase:check -- local
npm run supabase:check -- cloud

verify cobre testes automatizados do repositório, lint, tipos e build; não substitui as suites reais de Auth, RLS e sessão. supabase:check confirma o setup técnico. Com configuração e infraestrutura apropriadas, os comandos especializados são:

npm run auth:check -- local
npm run rls:check -- local
npm run auth:check-next -- local

Os runners têm requisitos distintos. auth:check envolve configuração administrativa restrita ao teste; RLS e Next exigem FIXIT_AUTH_SQL_COMMAND para preparação/limpeza; Next também exige Playwright/navegador por caminho explícito. Consulte o README antes de executar. Não coloque chave administrativa no frontend e não troque ambiente sem confirmar o destino.

Para apresentar uma evidência, registre versão/commit, ambiente, comando, resultado, limpeza e limite. Não diga “rodei e passou” se você apenas leu um relatório anterior.
